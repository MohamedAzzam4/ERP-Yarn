# Owner Decisions for Unresolved Questions

## 1. Transfer Model

Decision:

For MVP, use a one-step transfer model.

Meaning:

* Stock transfer immediately decreases the source location.
* Stock transfer immediately increases the destination location.
* Do not implement full in-transit dispatch/receive workflow in MVP.

However:

* Keep `in_transit` as a supported location type in the schema for future use.
* Do not design the database in a way that blocks future two-step transfer.

Final MVP rule:

```text
source location → destination location
```

Future-ready rule:

```text
source location → in_transit → destination location
```

Status:

```text
MVP = one-step transfer
Future = optional in-transit workflow
```

---

## 2. Factory Payable Recognition Event

Decision:

For MVP, factory payable should be recognized when production output receipt is approved.

Meaning:

* Sending material to the factory does not immediately create a factory payable.
* Worker/production user can record operational production data.
* Accountant/Owner confirms rate/cost and approves the production receipt.
* Factory payable is created after approved production receipt.
* For partial production receipts, payable is created only for the confirmed/approved consumed input quantity related to that receipt.

Required implementation rule:

Store a transaction snapshot on production records:

```text
payable_trigger_used = production_receipt_approval
factory_cost_basis_used = input_quantity
factory_rate_per_ton_used
calculation_version
confirmed_by
confirmed_at
```

Future change rule:

If the owner later decides that factory payable should be recognized at a different event, old approved transactions must not be recalculated or changed automatically.

Only new transactions should use the new rule after controlled configuration/change.

Status:

```text
MVP = factory payable on approved production receipt
Future = can support other trigger if added through controlled setup/configuration
```

---

## 3. Missing-Price Raw Receipt Behavior

Decision:

Raw material receipt should be allowed even if price is missing.

Meaning:

* Warehouse employee can record receipt quantity, supplier, location, batch number, and date.
* Stock is updated because the physical material exists.
* Supplier payable is not created until price is confirmed by Accountant/Owner.
* The record should be routed to Accountant Review.

Required behavior:

```text
stock movement = allowed
supplier payable = pending accountant review
financial completion = accountant/owner responsibility
```

Do not block operational stock entry only because financial price is missing.

Status:

```text
MVP = allow receipt without price, route financial completion to accountant review
```

---

## 4. Multi-Line Sales Requirement

Decision:

The database schema must support multi-line sales from the beginning.

Meaning:

Use:

```text
sales_orders
sales_order_lines
```

Do not design sales as a single item directly on the sales order table only.

However:

* MVP UI may start with one sales line per sale if this speeds up implementation.
* The schema and backend should not block adding multiple lines later.

Status:

```text
Schema/API = multi-line ready
MVP UI = may start single-line if needed
```

## 5. Approved Arabic Worker Terminology

Decision:

Use stable internal keys in the backend and configurable/replaceable Arabic labels in the UI.

Do not hardcode Arabic business labels inside business logic.

Create a terminology file/table with two levels:

```text
approved_terms
provisional_terms
```

Approved terms may be used directly in UI.

Provisional terms may be used only through terminology keys and must remain easy to change later.

Initial approved/probable terms:

```text
raw_batch = رسالة خام
single_yarn_lot = لوط فرد
twisted_yarn_lot = لوط زوى
single_yarn_factory = مصنع الفرد
twisting_factory = مصنع الزوى
inventory_movements = حركة مخازن
```

Terms needing confirmation can be marked provisional.

Important GLM rule:

* GLM must not block backend implementation waiting for final Arabic labels.
* GLM must not invent Arabic terms.
* GLM must use terminology keys and labels from the terminology file/table.

Status:

```text
Backend = stable keys
Frontend = Arabic labels from terminology layer
Unconfirmed labels = provisional, not hardcoded
```

## 6. Quality Statuses That Block Sales

Decision:

Keep quality workflow simple in MVP.

Quality status is an operational flag entered by workers.

It does not create financial decisions by itself.

Worker role:

* enters quality status
* enters notes/results
* does not decide financial discount
* does not decide profitability
* does not override sale restrictions

Owner/Accountant role:

* approves risky sale
* approves discount if needed
* handles financial/commercial decision

MVP statuses:

```text
accepted
needs_review
blocked
```

Rules:

```text
accepted → sale can proceed normally
needs_review → sale requires Owner/Accountant approval
blocked → sale is not allowed unless Owner/Accountant explicitly approves a special quality-risk sale
```

Do not overbuild advanced quality workflows in MVP.

Status:

```text
MVP = simple quality flags + approval guard
```

MVP should support simple return financial treatment options.

Supported MVP options:


Meaning:

* Worker can receive returned stock operationally.
* Accountant/Owner decides the financial treatment.
* Return approval posts stock impact.
* Financial impact is posted only after Accountant/Owner review/approval.

Returned stock should have a classification/status.

Suggested returned stock lifecycle:

```text
return_received
needs_quality_review
sellable_as_is
sellable_with_discount
blocked
reprocess_required
```

Status:

```text
MVP = simple return options, accountant/owner handles financial effect
```

## 9. Historical Migration Period, Reconciliation Totals, and Sign-Off

Decision:

Initial target historical migration period should be:

```text
2025 and 2026
```

Unless the owner later decides a different period.

Historical migration must not commit directly from messy Excel or AI output.

Required flow:

```text
messy sources
→ optional AI-assisted transformation
→ normalized templates
→ staging
→ validation
→ reconciliation
→ human review
→ Owner + Accountant approval
→ approved historical import commit
```

Sign-off authority:

```text
Owner + Accountant
```

Reconciliation totals must be provided or approved by Owner/Accountant before commit.

Reconciliation should include at least:

```text
raw material balances
single yarn balances
twisted yarn balances
stock by location
stock at external factories
customer balances
supplier balances
factory balances
sales totals
payment totals
production totals
known negative stock or mismatch warnings
```

Status:

```text
MVP = migrate 2025/2026 if available, with Owner + Accountant sign-off
```

## 10. Production Hosting Budget and Backup Recovery/Retention

Decision:

Free-tier hosting is allowed for development, demo, validation, and limited pilot only.

Free-tier must not be treated as production-ready.

Before real production go-live:

* use paid database/hosting plan if needed for reliability
* enable reliable backup
* run restore test
* define backup retention
* document recovery process

Minimum before pilot:

```text
manual database backup exists
restore test is executed or documented
file/import backup strategy exists
backup limitations are documented
```

Recommended before production:

```text
paid database plan
daily backups
restore test
minimum retention target: 30 days if budget allows
```

Important:

Exports are not backups.

Status:

```text
Development/Demo = free-tier allowed
Pilot = backup + restore test required
Production = paid/reliable hosting strongly required
```

## 11. Accountant User-Management Authority

Decision:

For MVP, only Owner can manage users and permissions.

Accountant may:

* view users if needed
* request user/permission changes
* manage financial and operational approvals
* manage payments/accounts/migration with permission

Accountant may not:

* change roles
* grant permissions
* create high-privilege users
* modify security settings

Status:

```text
MVP = Owner manages users and permissions
Accountant = no permission management
```

## 12. Export Usage

Decision:

For MVP, Excel/PDF exports are internal reports only.

They are not official/legal external documents unless explicitly designed later.

Meaning:

* exports can be used for internal review
* exports can show approval status
* exports are not backups
* exports are not official invoices/legal documents in MVP

If the business wants exports to be used externally or legally later, that should become a separate production-readiness/future scope item covering:

```text
official document numbering
fixed templates
legal wording
signatures/stamps
archiving
non-editable issued documents
```

Status:

```text
MVP = internal reports only
Future = external/legal document support if required
```

# Owner Decisions for Ambiguities Found in Final Implementation Plan v4

This document resolves the implementation ambiguities found in Final Implementation Plan v4.

These decisions should be treated as binding clarifications for the contract documentation and later GLM coding execution.

---

## 1. Negative Stock / `allowed_negative_flag`

### Ambiguity

Final Implementation Plan v4 mentioned an `allowed_negative_flag`, but this flag was not clearly defined.

This creates ambiguity:

* Is the flag on the tenant?
* Is it on the inventory balance?
* Is it on a stock movement?
* Who can enable it?
* Can workers use it?
* Does it allow negative stock silently?

### Final Decision

Do not implement a general user-editable `allowed_negative_flag`.

However, negative stock must be allowed to appear as a controlled data-integrity alert.

The original business decision is that negative stock should not be hidden. It should expose data-entry, timing, migration, or reconciliation problems.

### Correct Rule

```text
Negative stock is allowed to appear,
but it must never be invisible, silent, normal, or unreviewed.
```

### Required Rules

1. Negative stock must not be hidden.
2. Negative stock must appear in dashboard, approval, and reconciliation alerts.
3. Negative stock must not be silently auto-fixed.
4. Worker-entered operations may create potential negative stock only as draft / pending / needs-review records.
5. Owner/Accountant must review negative stock cases through:

   * Daily Approval
   * Inventory Adjustment
   * Historical Migration Review
   * explicit override where allowed
6. Sales approval must not silently create negative stock.
7. If sales stock is insufficient, approval should fail or require explicit Owner/Accountant override with reason and audit log.
8. Historical import may contain negative stock warnings, but commit requires explicit Owner/Accountant approval.
9. Negative customer/supplier/factory account balances are valid financial signs and are not inventory errors.
10. `reserved_qty_kg` must never be negative.
11. `wip_qty_kg` must not be negative except through explicit approved correction.

### Important Distinction

Inventory negative stock is a data-integrity warning.

Financial account negative balances are normal and expected under the signed amount convention.

Example:

```text
customer balance = -20,000
```

This may mean the customer has paid in advance or has a credit balance.

That is not an inventory error.

### Implementation Note

Do not expose a UI toggle called “allow negative stock”.

Instead, implement negative stock handling through approval, warning, audit, and reconciliation workflows.

## 2. Missing `approved_after_import_review` Enum Value

### Ambiguity

Final Implementation Plan v4 used the idea of:

```text
approved_after_import_review
```

But this value was not defined in the official approval status enum.

This creates ambiguity about whether a new approval status should be added.

### Final Decision

Do not add a new `approved_after_import_review` enum value.

Historical imported records should use existing status fields plus metadata.

### Correct Representation

For committed historical imported records, use:

```text
approval_status = approved
record_period = historical
record_origin = excel_import / ai_assisted_import / manual_historical_entry
is_locked = true
import_batch_id = required
```

### Example

A historical sale imported from Excel should be stored like this:

```text
sales_orders:
  doc_no = HIST-SALE-2025-001
  approval_status = approved
  record_period = historical
  record_origin = excel_import
  is_locked = true
  import_batch_id = IMPORT-2025-001
```

Meaning:

* `approved` means the record is approved.
* `historical` means it belongs to the past, not new live operations.
* `excel_import` means it came from a historical source file.
* `is_locked = true` means it cannot be edited directly.
* `import_batch_id` links it to the staging, validation, reconciliation, and approval process.

### Why This Is Better

This avoids creating many confusing approval statuses like:

```text
approved_after_import_review
approved_from_excel
approved_historical
approved_imported
```

The approval status remains simple, while the historical/import context is represented by separate fields.

## 3. Undefined `return_from_wip` Movement Type

### Ambiguity

Final Implementation Plan v4 mentioned returning unprocessed material from WIP, but `return_from_wip` was not clearly included as a stock movement type.

### Meaning of WIP

WIP means:

```text
Work In Progress
```

Arabic meaning:

```text
تحت التشغيل
```

or:

```text
قيد التصنيع
```

In this ERP, WIP means material that has left normal stock and entered production, but has not yet become finished output, waste, or returned stock.

### Example

Before production:

```text
Factory raw stock = 5000 kg
WIP = 0 kg
Single yarn stock = 0 kg
```

After issuing raw material to production:

```text
Factory raw stock = 0 kg
WIP = 5000 kg
Single yarn stock = 0 kg
```

After receiving production output:

```text
WIP = 0 kg
Single yarn stock = 4250 kg
Waste = 750 kg
```

### Return From WIP Scenario

If 5000 kg entered WIP, but the factory did not process 1000 kg and returned it as-is:

```text
WIP decreases by 1000 kg
Factory raw stock increases by 1000 kg
```

This should not be recorded as a vague inventory adjustment.

### Final Decision

Add explicit movement type:

```text
return_from_wip
```

### Responsibility

This is a controlled production correction, not a normal worker-only stock movement.

Production employee may create a draft/pending request when material issued to production was not processed and must return to normal stock.

If the material physically returns to an internal warehouse, Warehouse employee may confirm receipt/location.

If the material remains at the external factory, Production employee records the correction against the factory location.

Owner/Accountant must approve before the correction becomes posted.

### On Approval

The system must:

```text
WIP quantity decreases
on-hand stock at selected return location increases
stock movement with movement_type = return_from_wip is created
production order is updated
audit log is written
```

### Worker Restrictions

Workers must not enter:

* factory payable
* cost allocation
* profitability impact
* accounting entries

Any financial impact must be routed to Accountant Review.

## 4. Profitability Snapshot Mutation / Versioning

### Ambiguity

Final Implementation Plan v4 required profitability snapshots, but did not clearly define what happens if profitability changes later due to:

* return
* correction
* missing cost completion
* direct cost review
* payment/cost correction

### Final Decision

Profitability snapshots are immutable.

Do not edit old profitability snapshots directly.

If profitability needs to be recalculated, create a new snapshot version.

### Required Rule

```text
snapshot v1 = created at sale approval
snapshot v2 = created after return / correction / reviewed cost update
reports show latest active snapshot
old snapshots remain for audit
```

### Example

A sale is approved:

```text
sales_profitability_snapshot:
  sales_order_id = SALE-001
  version = 1
  profit = 20,000
  status = active
```

Later, a return happens and profit changes:

```text
sales_profitability_snapshot:
  sales_order_id = SALE-001
  version = 2
  profit = 12,000
  status = active
```

The old snapshot remains stored:

```text
version = 1
status = superseded
```

### Why

This prevents silent rewriting of historical profitability.

## 5. Gross vs Net Sales Revenue

### Ambiguity

Final Implementation Plan v4 mentioned revenue, discounts, and profitability, but did not clearly define whether profit uses revenue before or after discount.

### Final Decision

Store gross revenue, discount amount, and net revenue separately.

Profitability must use net revenue.

### Required Definitions

```text
gross_revenue = quantity × price
discount_amount = discount
net_revenue = gross_revenue - discount_amount
profitability uses net_revenue
```

### Example

```text
quantity = 1000 kg
price = 80,000 per ton
gross_revenue = 80,000
discount_amount = 5,000
net_revenue = 75,000
```

Profit must be calculated using:

```text
75,000
```

not:

```text
80,000
```

### Required Fields

Sales line or sales order should store:

```text
gross_revenue
discount_amount
net_revenue
```

## 6. Reservation Expiry Behavior

### Ambiguity

Final Implementation Plan v4 included `expires_at` for reservations, but did not define whether reservations expire automatically.

### Final Decision

Do not implement automatic reservation expiry in MVP.

A reservation remains active until one of these happens:

```text
sale approved
sale rejected
sale cancelled
manual release by authorized user
```

### Future-Ready Field

`expires_at` may exist as a nullable future field, but no automatic expiry job is required in MVP.

### Required MVP Behavior

```text
No automatic reservation expiry
No background job to release reservations
No silent stock release
Manual lifecycle only
```

### Why

This avoids a pending sale losing reservation silently due to an automatic job.

Automatic expiry can be added later after the business defines the exact policy.

## 7. Missing `approval_failed` Status

### Ambiguity

Final Implementation Plan v4 described approval failure cases, but did not define a clear status for when approval fails due to stock, reservation, validation, or transaction preconditions.

### Final Decision

Add status:

```text
approval_failed
```

### Meaning

`approval_failed` means:

```text
A user attempted approval, but the system could not complete the approval transaction safely.
```

This is different from:

```text
rejected
```

`rejected` means a human rejected the request.

`approval_failed` means the system could not approve it because a required condition failed.

### Example

A sale is pending approval.

At approval time, the system finds:

```text
reservation is invalid
or stock is insufficient
or item is blocked
```

Then:

```text
sales_order.status = approval_failed
audit log is written
Owner/Accountant can revise, cancel, or resubmit
```

### Required Rule

Approval failure must not create partial postings.

No stock movement, account entry, or profitability snapshot should be created if approval fails.

## 8. Returned Stock Classification Lifecycle

### Ambiguity

Final Implementation Plan v4 mentioned returned stock as sellable, blocked, or needing review, but did not define a clear lifecycle.

### Final Decision

Use a simple returned stock classification lifecycle in MVP.

### Supported Returned Stock Statuses

```text
return_received
needs_quality_review
sellable_as_is
sellable_with_discount
blocked
reprocess_required
```

### Rules

```text
sellable_as_is → available for normal sale
sellable_with_discount → sale requires Owner/Accountant approval
needs_quality_review → not available for sale until quality decision
blocked → not available for sale
reprocess_required → not available until processed/corrected
```

### Example

Customer returns yarn because of a complaint.

Initial status:

```text
return_received
```

Quality employee checks it.

If acceptable:

```text
sellable_as_is
```

If it can only be sold cheaper:

```text
sellable_with_discount
```

If not safe to sell:

```text
blocked
```

### Worker Role

Worker records the return and/or quality status.

Owner/Accountant decides financial treatment and approves risky resale if needed.

## 9. Master Data Deletion / Inactivation Rules

### Ambiguity

Final Implementation Plan v4 did not fully define whether master data can be deleted after it has been used.

This applies to:

* suppliers
* customers
* external factories
* locations
* fiber types
* product types
* quality parameters

### Final Decision

Do not hard-delete referenced master data.

Use inactive status.

### Required Rules

1. Referenced master data cannot be hard-deleted.
2. Inactive records remain visible in old documents.
3. Inactive records cannot be selected for new transactions.
4. If a duplicate exists, use alias/merge mapping with audit.
5. Do not break historical traceability by deleting old master data.

### Example

A factory was used in old production orders.

Do not delete it.

Instead:

```text
external_factories.status = inactive
```

Old production orders still show the factory.

New production orders cannot select it.

### Why

ERP records must remain traceable forever.

Deleting referenced master data would break old sales, production, stock movements, payments, and historical migration records.

# Final Summary of Approved Ambiguity Decisions

1. Do not implement a general user-editable `allowed_negative_flag`.
2. Negative stock must be visible as a controlled alert, not hidden or silently fixed.
3. Historical imported records use:

   * `approval_status = approved`
   * `record_period = historical`
   * `record_origin = excel_import / ai_assisted_import`
   * `is_locked = true`
   * `import_batch_id = required`
4. Add `return_from_wip` movement type.
5. Treat return from WIP as a controlled production correction requiring Owner/Accountant approval.
6. Profitability snapshots are immutable and versioned.
7. Store gross revenue, discount amount, and net revenue separately.
8. Profitability uses net revenue.
9. Do not implement automatic reservation expiry in MVP.
10. Add `approval_failed` status.
11. Use simple returned stock lifecycle:

    * `return_received`
    * `needs_quality_review`
    * `sellable_as_is`
    * `sellable_with_discount`
    * `blocked`
    * `reprocess_required`
12. Do not hard-delete referenced master data.
13. Use inactive status for old suppliers/customers/factories/locations/etc.
14. Workers record operational facts only.
15. Owner/Accountant handles approval, financial impact, overrides, and corrections.
