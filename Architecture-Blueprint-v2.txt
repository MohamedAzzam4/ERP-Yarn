# Architecture Blueprint v2

## Specialized Yarn Trading & Outsourced Manufacturing ERP

---

# 0. Project Context

We are building a specialized ERP system for a specific client working in the yarn and textile domain, especially yarn trading and outsourced yarn manufacturing.

The current client does not own internal production factories. Instead, the client buys raw fiber materials and sends them to external factories for single yarn production and twisted yarn production. These external factories also act as temporary inventory locations because materials and produced yarn can remain there for weeks or months before being transferred, sold, returned, further processed, or sold directly from the factory location.

However, the system should not be hardcoded for only this client. The long-term goal is to build a scalable and configurable ERP product that can later serve other yarn/textile trading and manufacturing clients with different workflows, terminology, costing rules, transport rules, approval rules, reporting needs, and operational constraints.

Therefore, the architecture should support:

* The current client’s actual workflow.
* Future clients with different outsourced manufacturing and reservation workflows.
* External factories as both service providers and inventory locations.
* Configurable terminology, warehouses, factories, users, reports, approval rules, backup policy, costing rules, transport payer rules, and profitability settings.
* A practical MVP that is close to the final product but avoids unnecessary complexity in phase one.
* A product foundation that avoids major refactoring when adapting the system for future companies.

The MVP should focus on the critical business value:

* Track raw material batches / رسائل خام.
* Track yarn lots / لوطات خيط.
* Manage internal and external inventory locations.
* Manage outsourced single yarn production and twisted yarn production.
* Track sales, payments, customer accounts, partial payments, and advance payments.
* Track supplier and external factory accounts.
* Track production costs separately from actual payments.
* Support factory production cost based on input quantity for the current client, while keeping the cost basis configurable for future clients.
* Track optional transport costs and allow flexible payer handling.
* Track quality, complaints, returns, and discounted or quality-risk sales approvals.
* Provide approximate profitability at first, with a configurable foundation for more accurate profitability later.
* Provide approval workflows, daily approvals, audit logs, and internal document numbering from day one.
* Support historical data migration from the client’s Excel files as approved historical imported records after validation and reconciliation.
* Preserve Arabic business terminology from the client’s existing Excel workbook as much as possible.
* Provide backup capability from MVP and test backup/restore, while allowing backup frequency to be configurable.

The MVP should be cloud-first and may use free-tier cloud deployment during validation to reduce early cost. Free-tier MVP hosting is intended for testing, demo, workflow validation, Excel migration validation, and client feedback. It should not be treated as the final production infrastructure.

The system should be production-minded even in MVP. It should not be a throwaway demo.

The correct balance is:

* Build simple enough to deliver the MVP quickly.
* Design core entities and workflows strongly enough to support real business operations.
* Avoid hardcoding business rules that are likely to differ across future clients.
* Avoid building a full dynamic rule engine too early.
* Store important rule snapshots inside transactions so future setting changes do not rewrite historical records.

# 2. Guiding Architecture Principles

## 2.1 Traceability First

The system must be built around traceability.

The most important question the ERP should answer:

Where did this material come from, where did it go, what was produced from it, who bought it, and did it cause quality or financial problems?

Traceability must work across:

* Raw material batch.
* Single yarn lot.
* Twisted yarn lot.
* Warehouse/location.
* External factory.
* Sales.
* Customer.
* Quality tests.
* Complaints.
* Returns.
* Financial impact.

## 2.2 Multi-location Inventory

Every physical place holding company-owned material must be modeled as an inventory location.

Locations include:

* Internal warehouse.
* Port warehouse.
* External single yarn factory.
* External twisting factory.
* Temporary warehouse.
* In-transit location.
* Returned stock location.

External factories are not only vendors. They are also temporary inventory locations.

## 2.3 Outsourced Production

Production is not internal manufacturing in the current client’s case.

The system must model production as outsourced transformation:

Raw Material Batch → External Single Yarn Factory → Single Yarn Lot
Single Yarn Lot → External Twisting Factory → Twisted Yarn Lot

The system must support:

* Sending material to an external factory.
* Keeping stock at the external factory.
* Receiving produced yarn.
* Tracking input quantity, output quantity, waste, and expected waste.
* Calculating production cost.
* Tracking factory performance.

## 2.4 Approval and Audit from Day One

The ERP must not allow silent destructive changes.

Important actions require approval or audit:

* Sales approval before execution.
* Daily approval for normal operational entries.
* Inventory adjustments.
* Returns.
* Discounts due to quality issues.
* Price changes.
* Quantity changes after approval.
* Reversing movements.
* Cancelling documents.
* Selling quality-risk stock.

Every important action must have an audit trail.

## 2.5 MVP Must Be Simple but Not Naive

The MVP should avoid overengineering, but the data model should not block future expansion.

For example:

* Current client usually produces a yarn lot from one raw material batch.
* Future clients may produce one yarn lot from multiple raw material batches.
* Current client usually produces one twisted lot from one single yarn lot.
* Future clients may combine multiple single yarn lots into one twisted yarn lot.

The MVP UI may support one-to-one input selection for simplicity, but the underlying data model should be many-to-many capable where needed.

# 5. Core Workflows

## 5.1 Raw Material Purchase and Receipt

Flow:

1. Create raw material batch.
2. Enter supplier, material type, origin, number of bales, weights, purchase price.
3. Generate internal document number.
4. Receive into a location.
5. Create stock movement.
6. Add quality test if available.
7. Mark as pending daily approval.
8. Owner/accountant approves at end of day.
9. Record becomes approved and locked.

MVP:

* Manual entry.
* Excel import supported.
* Documents optional.

Future:

* Supplier portal.
* OCR.
* Purchase order module.

## 5.2 Transfer to External Factory

Flow:

1. Select raw material batch or yarn lot.
2. Select source location.
3. Select external factory location.
4. Enter quantity.
5. Create transfer movement.
6. Stock appears at destination location.
7. Movement enters daily approval.

Important:

* Source can be internal warehouse, port warehouse, or another factory.
* Destination can be external factory.
* Transport cost can be optional in MVP.

## 5.3 Single Yarn Production

Flow:

1. Create production order.
2. Select raw material batch input.
3. Select external single yarn factory.
4. Enter input quantity.
5. Create issue-to-production movement.
6. Material remains tracked at factory location.
7. Enter output single yarn lot when production is received.
8. Enter output quantity.
9. System calculates waste.
10. System creates single yarn lot.
11. System updates inventory.
12. Order enters daily approval.

Important:

* One raw batch may be split across many factories.
* One raw batch may produce multiple single yarn lots.
* MVP UI may select one input batch per production order.

## 5.4 Twisted Yarn Production

Flow:

1. Create twisting order.
2. Select single yarn lot input.
3. Select twisting factory.
4. Enter input quantity.
5. Create issue-to-twisting movement.
6. Enter output twisted yarn lot.
7. Enter output quantity.
8. System calculates waste.
9. System creates twisted yarn lot.
10. System updates inventory.
11. Order enters daily approval.

Important:

* One single yarn lot can be split into multiple twisted yarn lots.
* Future model should support one twisted lot from multiple single yarn lots.
* MVP UI can support one input single yarn lot.

## 5.5 Sale Approval Workflow

All sales require approval before execution.

Flow:

1. User creates sales request.
2. Select customer.
3. Select product: raw material, single yarn, or twisted yarn.
4. Select source batch/lot.
5. Select source location.
6. Enter quantity.
7. Enter price per ton.
8. Enter payment terms.
9. System shows quality warnings and stock warnings.
10. Request status becomes pending approval.
11. Owner/accountant reviews.
12. If approved:

    * Stock is reduced.
    * Customer account is updated.
    * Sale becomes approved.
    * Document becomes printable/exportable.
13. If rejected:

    * No stock impact.
    * No customer account impact.

Important:

* Sales can happen from external factory locations.
* Quality-risk sales require visible warning and approval.
* Discounted sales require approval.

## 5.6 Return Workflow

Flow:

1. Create return request.
2. Link to sale if possible.
3. Select returned item and quantity.
4. Enter reason.
5. Enter return location.
6. Mark resale status.
7. Request approval.
8. If approved:

   * Stock is returned to inventory.
   * Customer account is adjusted if needed.
   * Return is linked to complaint if applicable.

Important:

Returned stock is not automatically waste. It usually returns as inventory but with condition/status.

## 5.7 Daily Approval Workflow

Normal operational entries can be entered during the day and reviewed later.

Daily approval includes:

* Raw material receipts.
* Stock transfers.
* Production entries.
* Production receipts.
* Quality entries.
* Normal inventory movements.

Flow:

1. Data-entry users enter operations.
2. Operations appear as unapproved.
3. Owner/accountant opens Daily Approval screen.
4. Reviews grouped operations.
5. Approves, rejects, or requests correction.
6. Approved records become locked.
7. Later changes require approval and audit log.

MVP display:

* Show current stock with a badge that some movements are unapproved.
* Do not build separate approved/unapproved stock balances in MVP.

Future:

* Approved balance.
* Pending movement balance.
* Expected balance.

## 5.8 Inventory Adjustment Workflow

Sensitive workflow.

Flow:

1. User creates adjustment request.
2. Enters reason.
3. Shows current quantity and adjusted quantity.
4. Requires approval.
5. If approved:

   * Adjustment movement is created.
   * Audit log is recorded.

Adjustment examples:

* Stock count difference.
* Negative balance correction.
* Weight correction.
* Data entry correction after approval.

## 5.9 Quality-risk Sale Workflow

If item quality status is:

* Needs review.
* Rejected.
* Returned.
* Under complaint.

Then sale is allowed only with explicit approval.

Flow:

1. User creates sale request.
2. System detects quality warning.
3. Warning appears.
4. Sale requires approval.
5. Approval record stores reason.

## 5.10 No Silent Delete Workflow

Important records should not be hard-deleted.

Instead:

* Cancel.
* Reverse.
* Adjust.
* Mark inactive.
* Create audit record.

Applies to:

* Stock movements.
* Sales.
* Production orders.
* Returns.
* Adjustments.
* Payments.

# 7. Document Numbering

Every major transaction must have an internal document number.

Suggested formats:

* RM-YYYY-0001: Raw material receipt.
* TR-YYYY-0001: Stock transfer.
* PROD-S-YYYY-0001: Single yarn production.
* PROD-T-YYYY-0001: Twisted yarn production.
* SO-YYYY-0001: Sales order/request.
* PAY-YYYY-0001: Payment.
* RET-YYYY-0001: Return.
* ADJ-YYYY-0001: Inventory adjustment.
* QC-YYYY-0001: Quality test.
* CMP-YYYY-0001: Complaint.
* APR-YYYY-0001: Approval request.

All printed/exported documents must show approval status:

* Draft.
* Pending approval.
* Approved.
* Rejected.
* Cancelled.
* Reversed.

# 8. Inventory Rules

## 8.1 Storage Unit

The internal storage unit should be kilograms.

The UI can display:

* kg.
* tons with decimal values.

Example:

12,450 kg = 12.45 tons.

## 8.2 Negative Stock

Negative stock should not be hidden.

Rules:

* Allow negative balance to appear.
* Highlight it as critical.
* Show it in dashboard alerts.
* Require review and adjustment.
* Do not silently auto-fix.

## 8.3 Stock Statuses

Suggested statuses:

* Available.
* In production.
* At external factory.
* In transit.
* Sold pending approval.
* Sold.
* Delivered.
* Returned.
* Needs quality review.
* Quality rejected.
* Cancelled/reversed.

## 8.4 Current Location

Every item quantity must be traceable to a location.

A single batch or lot can have quantities distributed across multiple locations.

Example:

Raw batch R-2025-001:

* 5 tons in Alexandria warehouse.
* 8 tons at Single Yarn Factory A.
* 3 tons at Single Yarn Factory B.
* 2 tons sold.

# 9. Financial Rules

## 9.1 MVP Profitability

Profitability is approximate in MVP.

Approximate profit formula:

Sales revenue
minus raw material cost
minus single yarn production cost
minus twisting cost
minus optional direct transport cost
minus optional return/discount impact

## 9.2 Future Accurate Profitability

Future version should support:

* Transport allocation.
* Storage cost.
* Customs.
* Commissions.
* Financing cost.
* General overhead allocation.
* Waste cost.
* Complaint cost.
* Return cost.
* Multi-currency if needed.

## 9.3 Customer Accounts

Must support:

* Advance payments.
* Partial payments.
* Short-term credit.
* Remaining balance.
* Payment history.
* Customer statement.

## 9.4 Supplier and Factory Accounts

Must support:

* Supplier purchases.
* Factory production costs.
* Payments.
* Remaining balances.
* Optional deductions or adjustments.

Current client usually absorbs factory mistakes, but the system should allow future adjustments.

## 9.5 Export Permissions

Only owner and accountant can export:

* Excel.
* PDF.
* Financial reports.
* Customer statements.
* Profitability reports.

## Data Migration, Terminology, Backup, and Cost Handling Addendum

### 1. Historical Data Migration Strategy

The system must include a dedicated Historical Data Migration & Reconciliation subsystem.

This subsystem is not a daily operational module for normal users. It is an admin/accountant/owner tool used to import and validate historical data from the client’s Excel files, mainly for 2025 and 2026.

Historical imported records must be imported as:

* Approved
* Historical
* Imported

They should not enter the normal approval workflow, because they represent past business activity. However, they must still have an import audit trail.

Each imported record should include:

* Source Excel file name
* Source sheet name
* Source row number
* Import batch ID
* Imported by
* Imported at
* Validation status
* Mapping version
* Notes or warnings

The import process should prioritize correctness over speed.

The implementation should not leave migration design until the end. The migration strategy, required Excel sheets, required columns, validation rules, and mapping rules must be designed early. However, the full import tool can be implemented near the end after the core entities and workflows are stable.

Recommended execution order:

1. Define Excel sheet mapping early.
2. Define validation rules early.
3. Build the core ERP modules.
4. Build the historical import tool near the end.
5. Import 2025/2026 data into staging/draft migration tables.
6. Validate and reconcile imported data.
7. Approve the import as historical approved records.
8. Use the ERP as the source of truth after go-live.

Old Excel data should be treated as a migration and reconciliation reference. After go-live, the ERP should become the operational source of truth.

# Architecture Decision Addendum

## Binding Business & Productization Decisions

This addendum is part of the Architecture Blueprint and should be treated as authoritative for the Implementation Plan and Attack Review.

The system is being built for one specific yarn trading and outsourced manufacturing client first, but it must also remain productizable for future textile/yarn clients with different business rules.

The MVP should stay practical and avoid overengineering, but the architecture must not hardcode business rules that are likely to vary across future clients.

---

## 1. Cloud-First Deployment

Decision:

The system is cloud-first.

Rationale:

The client needs access from multiple roles and locations. The system should be easy to demo, test, and operate without depending on a local machine inside the company.

Architecture impact:

* No local-only architecture in MVP.
* No offline sync engine in MVP.
* Must include cloud security, role-based access, environment configuration, database backup, file backup, and production upgrade path.
* Local/offline support is future scope unless later required.

---

## 2. Free-Tier MVP, Production-Minded Architecture

Decision:

The MVP may use free-tier cloud deployment where possible.

Rationale:

The goal is to validate workflow, data model, Excel migration, approvals, and traceability with minimal cost before committing to paid infrastructure.

Important nuance:

Free-tier MVP does not mean throwaway architecture.

Architecture impact:

* The system must be built so it can move to paid production hosting without major refactoring.
* Free-tier limits must be documented.
* Backup and restore capability must be tested.
* Real production use requires a clear upgrade path.
* Business data must not be trapped in a weak hosting setup.

---

## 3. Modular Monolith

Decision:

Use a modular monolith for MVP.

Rationale:

The project needs fast delivery, simpler debugging, strong consistency, easier testing, and lower complexity for AI-assisted development.

Architecture impact:

* Avoid microservices in MVP.
* Define clear module boundaries.
* Keep business logic out of UI components.
* Use service/domain layers for core rules.
* Use transactions for workflows that affect stock, accounts, approvals, or audit logs.

---

## 4. PostgreSQL / Relational Database

Decision:

Use a relational database, preferably PostgreSQL.

Rationale:

The domain is highly relational and transactional.

Architecture impact:

The database must safely model:

* Raw material batches.
* Yarn lots.
* Stock movements.
* Production orders.
* Sales.
* Payments.
* Quality tests.
* Complaints.
* Returns.
* Approvals.
* Audit logs.
* Traceability.

A purely document-based database should not be used for the core ERP data model.

---

## 5. External Factories as Inventory Locations

Decision:

External factories must be modeled as inventory locations.

Rationale:

The client’s materials and produced yarn can remain at external factories for weeks or months. Even though factories are vendors/service providers, they also physically hold company-owned stock.

Architecture impact:

* External factories must have inventory balances.
* Stock can exist at internal warehouses, port warehouses, external factories, in-transit locations, and return locations.
* Production and stock reports must show factory-held stock.
* Sales can occur from stock located at an external factory.

---

## 6. Historical Data Imported as Approved Historical Records

Decision:

Historical data should be imported as:

* Approved.
* Historical.
* Imported.

It should not go through the normal per-record approval workflow.

Rationale:

The data represents past business activity. Re-approving every historical sale, movement, production order, or payment one by one would be operationally unrealistic.

Important nuance:

Approved historical import does not mean unsafe import.

Architecture impact:

* Historical data must pass strong validation and reconciliation before commit.
* Each imported record must store source file, source sheet, source row, import batch ID, imported by, imported at, and validation status.
* Imported records should be locked after commit.
* Corrections after import should happen through adjustments, reversals, or audited correction flows.
* Historical records should not be silently recalculated later.

---

## 7. Historical Migration Designed Early, Tool Built Later

Decision:

Historical migration strategy must be designed early, but the full import tool can be implemented near the end.

Rationale:

The system cannot design entities blindly and later discover that Excel data cannot map into them. However, building the full import tool before core entities stabilize may waste effort.

Architecture impact:

* Early phase must define Excel sheet mapping.
* Early phase must define mandatory columns.
* Early phase must define validation rules.
* Early phase must define staging/import tables.
* Full migration tool can be built after core modules stabilize.
* Migration and reconciliation must happen before go-live.

---

## 8. Arabic Terminology Based on Existing Excel Workbook

Decision:

Arabic terminology should be based on the client’s current Excel workbook.

Rationale:

The client already uses specific business terms, and changing them unnecessarily will make adoption harder.

Core terminology includes:

* مبيعات خامات

* انتاج الزوى وتوزيعه

* شكاوى العملاء

* لوط الفرد
* مصنع الزوى
* سعر تشغيل الطن
* ثمن التشغيل جنيه
* وزن قائم الرسالة
* عدد بال الرسالة
* نمرة الخيط المزوى Ne

## 9. Factory Cost Basis for Current Client

Decision:

For the current client, external factories are paid based on input quantity sent to the factory, not output quantity produced.

Formula:

factory_cost = input_quantity_kg / 1000 × factory_cost_per_input_ton

Rationale:

This reflects the current client’s real business practice.

Architecture impact:

* Waste must not reduce factory payable for the current client.
* Factory payable must be created based on input quantity.
* Profitability must use input-based factory cost.
* The cost rule used must be snapshotted on each production order.
* Production output quantity is still used for inventory and waste calculation, not for factory payable calculation for this client.

---

## 10. Configurable Factory Cost Basis for Future Clients

Decision:

Even though the current client uses input quantity, the system should support future configuration.

Supported future cost bases:

* input_quantity
* output_quantity
* fixed_amount
* manual_amount

Rationale:

Other companies may pay factories differently.

Architecture impact:

* Do not hardcode input_quantity in a way that blocks future clients.
* Do not build a complex rule engine in MVP.
* Use simple settings/defaults.
* Allow per-factory override if needed.
* Snapshot the cost basis on the production order.
* Future clients should not require major refactoring to use another cost basis.

---

## 11. Transport Cost Flexibility

Decision:

Transport cost should be optional in MVP and flexible in ownership.

Possible payer types:

* Company.
* Customer.
* External factory.
* Shared.
* Other.
* Unknown.

Rationale:

Transport cost may be split between parties, paid by the client company, paid by the customer, paid by the factory, or handled differently per case.

Architecture impact:

* Transport cost should not block stock movement in MVP.
* Transport can be attached to movement, production, sale, or return.
* Payer type must be stored.
* Split payment should be possible or future-compatible.
* Transport can optionally affect profitability.
* Missing transport cost should not break core operations.

---

## 12. Profitability Must Be Configurable but Not Overengineered

Decision:

Profitability should be configurable over time, but MVP should use a clear simple formula.

MVP default may include:

* Raw material cost.
* Single yarn production cost.
* Twisting cost.
* Transport cost if entered.
* Discounts.
* Return impact.

Future versions may include:

* Storage.
* Customs.
* Commissions.
* Financing.
* Overhead allocation.
* Complaint compensation.
* Multi-currency effects.

Rationale:

Different companies calculate profitability differently.

Architecture impact:

* MVP should clearly label profitability as approximate.
* Cost components should be configurable enough for future expansion.
* Profitability calculations should snapshot inputs used at calculation time.
* Historical profitability should not silently change when settings change later.

---

## 13. Costs and Payments Must Be Separate

Decision:

Costs should be recorded independently from payments.

This applies to:

* Factory production cost.
* Twisting cost.
* Transport cost.
* Supplier purchases.
* Other direct costs.

Rationale:

The client may pay costs immediately, after around two weeks, partially, or later. The system should not assume immediate payment.

Architecture impact:

* Creating a cost does not mean it is paid.
* The system must support unpaid, partially paid, and paid statuses.
* Payment records must be separate from cost records.
* Factory, supplier, and transport account statements should be possible.

---

## 14. Backup Design for MVP

Decision:

Backup capability must be designed from MVP and tested during MVP.

Important nuance:

Daily backup is recommended for production. In free-tier MVP, daily automated backup may not be a hard blocker from day one, but backup and restore capability must exist and be tested.

Architecture impact:

* User exports are not backups.
* Database backup and file backup must be considered separately.
* Imported Excel source files and migration logs must be included in backup planning.
* Restore testing must be part of the plan.
* Production upgrade path must include reliable automated backups.
* Backup operations should be audited where appropriate.

---

## 15. Configurable Backup Frequency

Decision:

Owner/Admin should be able to configure backup policy.

Possible frequencies:

* Manual.
* Daily.
* Weekly.
* Monthly.

Rationale:

Different clients and deployment plans may need different backup frequencies.

Architecture impact:

* Backup settings must not be fake UI.
* Backup frequency should map to real implementation behavior.
* Production should support daily or better backups.
* MVP should at least prove manual or scheduled backup and restore.
* Report exports must not be treated as backup.

---

## 16. Flexibility Without Making Everything Dynamic

Decision:

The system should be designed for future configurability, but MVP should not make everything dynamic from day one.

Rationale:

Overengineering will slow the MVP and make it fragile. Underengineering will make future client customization expensive.

Architecture impact:

* Stable core domain model.
* Likely-to-change business rules should be settings.
* Transactions must store snapshots of rules used at creation time.
* Sensitive setting changes must be audited.
* Advanced rule engines are future scope.
* Historical records should not be recalculated silently.
* Use tenant default, factory override, and transaction override where appropriate, but keep MVP implementation simple.

---

## 17. Approved Decision Hierarchy

If the Blueprint, Implementation Plan, and Reviewer Context appear to differ, use this hierarchy:

1. Architecture Blueprint + Architecture Decision Addendum.
2. Explicit approved business decisions from the conversation.
3. Implementation Plan.
4. Reviewer Context.

The Reviewer Context explains how to review decisions, but the Blueprint/Addendum defines the decisions themselves.
