# 0. Purpose

This document integrates the findings from two independent architecture attack reviews of Implementation Plan v3.

The goal is not to blindly apply every attack finding.

The goal is to decide:

1. Which findings must be accepted.
2. Which findings should be accepted with reduced scope.
3. Which findings are useful but should be deferred.
4. Which findings should be rejected or modified because they create unnecessary MVP risk.
5. What the Final Implementation Plan v4 must include to become safe enough for AI-assisted implementation.

# 1. Final Direction After Attack Reviews

Implementation Plan v3 is directionally strong, but it is not yet safe enough as an execution document.

The main weakness is that v3 says the right things at a high level, but does not define enough execution rules for:

* database schema
* inventory posting
* stock balances
* approval transactions
* production WIP
* customer/supplier/factory balances
* historical Excel migration
* backup and restore
* permission enforcement
* testing
* AI coding safety

Therefore, v4 must not simply be a longer plan.

v4 must become:

```text
Final Implementation Plan v4
+
Execution-Safe Architecture Details
```

# 2. Major Scope Correction

## 2.1 Reduce Runtime Configurability in MVP

The previous direction leaned toward a configurable ERP product.

This is too risky for MVP.

Final decision:

```text
The MVP is a single-client ERP implementation with future-ready architecture.
It is not a fully configurable ERP product from day one.
```

Meaning:

* Current client rules should be fixed during setup.
* Sensitive business settings should not be freely editable by normal users in MVP.
* Future configurability should be designed structurally, but not fully exposed.
* No full dynamic rule engine in MVP.
* No user-editable financial formulas in MVP.
* No runtime-changing factory cost basis from UI in MVP.
* No user-editable profitability formula in MVP.

The system should still avoid hardcoding rules deeply into business logic.

Use:

* internal configuration
* setup-time defaults
* transaction snapshots
* audit logs
* controlled technical change process

Do not expose dangerous settings as open UI features.

# 3. Configuration Levels

## Level 1 — Safe MVP Settings

These can exist in MVP UI:

* company profile
* users
* roles
* permissions
* suppliers
* customers
* locations
* external factories
* product/fiber types
* basic terminology labels
* backup frequency if technically supported
* document numbering prefixes if simple and safe

## Level 2 — Restricted Business Settings

These may exist internally or as read-only in MVP:

* factory cost basis
* default factory rate
* default transport payer
* profitability profile
* approval thresholds
* transport inclusion in profitability
* backup policy details

These should not be freely editable by workers.

If shown to Owner, they should be read-only or changeable only through a controlled process.

## Level 3 — Dangerous Runtime Settings

Defer to future productization:

* changing factory cost basis after live transactions exist
* dynamic profitability formulas
* rule engine
* effective-dated rules per factory/product/client
* automatic historical recalculation
* arbitrary custom financial rules
* user-defined accounting logic

# 4. Worker Data-Entry UX Simplification Principle

The ERP must separate operational data entry from financial/accounting complexity.

Warehouse, production, and quality employees should only see simplified role-specific screens.

They should enter operational facts, not accounting interpretations.

## Worker-facing screens should avoid exposing concepts such as:

* cost allocation
* actual payer
* receivables
* payables
* settlement
* profitability
* financial reconciliation
* accounting adjustments
* profitability profile
* cost formula version

## Worker-facing screens should prioritize:

* Arabic-first terminology
* minimum required fields
* sensible defaults
* fast entry
* optional financial fields when appropriate
* “unknown” option
* “needs accountant review” option
* clear validation messages
* no profitability visibility
* no financial reports
* no advanced settings

## Accountant/Owner screens should handle:

* actual payment
* payable impact
* receivable impact
* settlement
* cost allocation
* profitability treatment
* correction
* reversal
* reconciliation
* audit review

## Important rule

If a worker enters incomplete or uncertain financial-related data, the operational record should still be saved when safe, and routed to accountant review instead of blocking the workflow unnecessarily.

# 5. Accepted as MVP Blockers

These must be fixed in v4 before implementation begins.

## 5.1 Real Database Schema Draft

v4 must include implementation-grade schema details, not only table names.

Required:

* important columns
* foreign keys
* unique constraints
* tenant scoping
* indexes
* enums
* check constraints
* soft delete / cancel / reversal rules
* immutable document numbers
* audit relationships

## 5.2 Inventory Ledger and Balance Model

v4 must define one canonical inventory model.

Preferred model:

```text
stock_movements = immutable source of truth
inventory_balances = materialized/derived balance updated transactionally
```

Must define:

* on-hand quantity
* reserved quantity
* available quantity
* WIP quantity
* returned quantity
* blocked quantity
* negative stock behavior
* reconciliation from ledger
* approval impact on stock
* idempotency rules

## 5.3 Pending Sales Reservation

Pending sales must not reduce official stock, but they must prevent double-selling.

v4 must define:

* reserved quantity
* available-to-sell quantity
* atomic stock re-check at approval
* failure behavior if stock becomes unavailable
* optional owner/accountant override for special cases

## 5.4 Production Posting and WIP Model

v4 must define production stock movement semantics.

Must cover:

* material at external factory
* issue to production
* WIP
* output receipt
* waste posting
* remaining unprocessed stock
* partial production
* partial receipt
* relationship between raw batch, single yarn lot, twisted yarn lot

Avoid double-counting or losing factory-held stock.

## 5.5 Atomic Approval Transactions

Every approval/posting action must be a single safe database transaction.

Applies to:

* sales approval
* return approval
* inventory adjustment approval
* production receipt approval
* post-approval correction
* reversal
* historical import commit

Must include:

* state transition check
* database transaction
* row locking where needed
* idempotency key
* stock/account side effects
* audit log written in the same transaction
* duplicate approval prevention

## 5.6 Financial Subledger Rules

v4 must define customer, supplier, and factory balance logic.

Must include:

* immutable account entries
* signed amount convention
* source document type/id
* debit/credit or positive/negative direction
* partial payments
* advance payments
* settlement links
* reversal entries
* balance views
* reconciliation reports

This is not a full accounting ledger, but it must be a reliable operational subledger.

## 5.7 Supplier Payable on Raw Material Purchase/Receipt

If supplier balances are in MVP scope, then supplier payable creation must not wait until Phase 5.

Raw material purchase/receipt approval should create:

* stock movement
* supplier payable entry
* audit log

in the same transaction.

If price is missing in historical data, mark it for accountant review.

## 5.8 Workbook-Specific Historical Migration

Do not assume clean import sheets only.

The current workbook has business sheets, embedded master data, formulas, multi-row headers, blank cells, mixed dates, and inconsistent labels.

v4 must define workbook-specific migration for actual sheets such as:

* خام
* مبيعات خامات
* انتاج الفرد وتوزيعه
* انتاج الزوى وتوزيعه
* حركة المخازن
* شكاوى العملاء
* جودة الخيوط
* جودة الخامات

Clean normalized import templates can be future target templates, not the assumption for current migration.

## 5.9 Master Data Extraction from Excel

Because suppliers, customers, factories, and locations may be embedded in transaction sheets, v4 must include a master-data extraction stage.

Must include:

* extract candidate suppliers
* extract candidate customers
* extract candidate factories
* extract candidate locations
* alias mapping
* deduplication
* manual approval by Owner/Accountant
* mapping old names to normalized master records

## 5.10 Historical Formula Handling

For imported Excel data, the system must not blindly import visible values only.

Migration staging should preserve:

* original cell value
* formula text if present
* calculated value
* source sheet
* source row
* mapped ERP meaning
* validation warning if formula implies hidden business assumption

## 5.11 Historical Factory Cost Preservation

New live transactions should use the current client rule:

```text
factory cost = input quantity × rate
```

But historical Excel records may have been calculated differently.

For historical imported production records:

* preserve original Excel total factory cost
* do not force recalculation
* store imported cost as historical value
* store calculation basis source

Use fields such as:

```text
imported_total_factory_cost
historical_cost_basis_source
calculation_basis_source
source_formula_text
migration_warning
```

Allowed historical basis values:

```text
imported_excel
input_based
output_based
manual
unknown
```

This is not a general user override.

It is historical cost preservation.

## 5.12 Permission Matrix

v4 must include a real permission matrix.

Must cover:

* module-level permissions
* action-level permissions
* field-level financial visibility
* export permissions
* report permissions
* API permissions
* audit visibility

Important fields to protect:

* prices
* costs
* profitability
* customer balances
* supplier/factory balances
* financial reports
* exports
* settings
* audit logs

## 5.13 Minimal Backup and Restore Before Pilot Data

Backup design in Phase 0 is not enough.

Before real pilot data or real migration data is entered, the system must support:

* manual database backup
* file/import backup or documented equivalent
* restore test
* backup evidence/log
* known free-tier limitations

Advanced backup UI can remain later.

## 5.14 Executable Test Cases

v4 must include executable tests with inputs and expected outputs.

Not only checklist items.

Must include:

* stock tests
* production tests
* sales approval tests
* return tests
* payment tests
* supplier/factory balance tests
* migration tests
* permission tests
* backup/restore tests
* concurrency tests
* idempotency tests

## 5.15 High-Risk API Contracts

v4 must not list routes only.

For high-risk endpoints, define:

* required permission
* request shape
* response shape
* validation rules
* state preconditions
* database transaction effects
* audit events
* idempotency behavior
* forbidden fields by role

# 6. Accepted as High Priority / Production Blockers

These should be designed in v4, even if not fully implemented in the earliest MVP phase.

## 6.1 Many-to-Many Production Model

MVP UI may start simple, but schema must not block:

* one raw batch to multiple single yarn lots
* one single yarn lot to multiple twisted lots
* multiple input rows per production order
* future blending/combinations

Do not implement schema shortcuts like one input_lot_id directly on production_order only.

## 6.2 Factory Rate Selection

Because factory rates may change, v4 must define how production rates are selected.

MVP acceptable approach:

* factory default rate is suggested
* user/accountant confirms rate on production order
* confirmed rate is snapshotted
* changing default rate affects only future orders

Future approach:

* effective_from/effective_to pricing rules

## 6.3 Sales Profitability Snapshot

Changing profitability settings later must not silently rewrite historical approved sales profitability.

v4 must store enough snapshot data at sale approval or report-finalization time.

Possible fields/table:

* sales_profitability_snapshot
* raw_cost_snapshot
* production_cost_snapshot
* twisting_cost_snapshot
* transport_cost_snapshot_if_known
* discount_snapshot
* return_impact_snapshot
* profitability_profile_version
* calculated_at

Keep MVP profitability approximate but deterministic.

## 6.4 Direct Cost Allocation vs Actual Payment

Internally, the system must separate:

```text
who should bear the cost
```

from:

```text
who actually paid
```

But do not expose this complexity to workers.

Use internal concepts:

* cost responsibility
* allocation/share
* actual payer
* payable
* receivable
* settlement

Worker UI should only ask simple operational questions.

## 6.5 Transport Posting Scenarios

Transport is optional in MVP.

If entered, v4 must define limited safe scenarios:

* company-borne cost
* customer-borne receivable
* factory-borne deduction/receivable
* shared split
* unknown / needs accountant review
* included elsewhere

If transport behavior is uncertain, save operational record and send financial side to accountant review.

## 6.6 Deterministic MVP Profitability

Approximate profitability must still be deterministic.

v4 must define:

* raw cost per kg
* output effective cost per kg
* production cost allocation
* waste treatment
* transport inclusion rule
* discounts
* return impact
* unknown/missing cost behavior
* profile/version shown on report

Avoid building a full cost accounting engine.

## 6.7 Append-Only Audit Log

Audit logs should be append-only.

They must be written in the same transaction as important business changes.

Normal app users should not be able to edit or delete audit logs.

Audit visibility should be restricted.

## 6.8 Historical Correction Workflow

Historical records are locked after import.

v4 must define how corrections happen:

* correction request
* approval
* reversal or adjustment
* link to original imported record
* audit log
* no direct editing of imported approved records

## 6.9 Reversal and Post-Approval Correction APIs

v4 must include workflows/endpoints/contracts for:

* reverse inventory movement
* request sales change
* request production correction
* reverse payment
* request raw batch correction
* reverse return/adjustment if needed

## 6.10 Document Numbering Concurrency

v4 must define how document numbers are generated safely.

Use:

* database sequences
* locked sequence rows
* tenant/document-type/year scoping
* uniqueness constraints
* concurrency tests

## 6.11 Logical Date Validation

Historical migration must validate logical dates, not only date format.

Examples:

* sale_date should not be before receipt_date unless explicitly accepted as historical inconsistency
* production_date should not be before material availability
* payment_date should be checked against related sale/account context
* return_date should not be before sale_date

Allow historical warning/exception only with explicit approval.

## 6.12 Quality Mapping Rules

Quality migration must map lab-like Excel columns properly.

v4 must define:

* quality parameter code
* Arabic label
* English label
* unit
* source column
* acceptable range
* result interpretation
* status mapping

## 6.13 Thin Traceability Earlier

Full traceability screen can remain later, but a thin traceability slice must appear earlier.

Suggested:

* Phase 2: raw batch timeline
* Phase 3: movement timeline
* Phase 4: production lineage
* Phase 5: sale/customer linkage
* Phase 6: complaint/return linkage
* Phase 8: full traceability screen/report

## 6.14 Terminology Caching

Terminology labels should not be fetched from the database on every page load.

MVP strategy:

* fetch terminology once at login/app start
* store in frontend state/context
* refresh when settings change
* provide fallback labels in code

# 7. Accepted with Scope Limitation

## 7.1 In-Transit Inventory

Do not implement full two-step in-transit workflow in MVP unless the client explicitly needs it.

MVP can use one-step transfer.

If one-step transfer is used, document the limitation clearly.

Future:

* dispatch
* in-transit location
* receive at destination
* cancel/loss/delay handling

## 7.2 Backup Automation

Do not require full daily automated backup in free-tier MVP.

But require:

* backup capability
* restore test
* documented limits
* production upgrade checklist

## 7.3 Global Smoke Test

The 44-step global smoke test is too large to run after every phase.

Use:

* phase-specific smoke tests after each phase
* full regression before demo/pilot/go-live

## 7.4 Transport Cost

Transport remains optional in MVP.

Do not block stock movement if transport cost is missing.

Use:

* unknown
* not recorded
* included elsewhere
* needs accountant review

## 7.5 Profitability

Profitability in MVP is approximate.

Do not build a full accounting or costing engine.

But the approximation must be deterministic, documented, and tested.

# 8. Modified or Rejected Attack Suggestions

## 8.1 Do Not Delete Audit Logs Unsafely

One attack suggested archiving/deleting old audit logs from the operational database to survive free-tier limits.

Reject unsafe deletion.

Better approach:

* keep audit logs append-only
* document free-tier limits
* limit pilot usage
* upgrade before heavy production
* future immutable archive can be designed carefully

## 8.2 Rename Historical Cost Override

Avoid calling it “override” in a way that implies users can freely overwrite costs.

Use:

```text
Imported Historical Cost Preservation
```

or:

```text
As-Is Historical Cost Import
```

## 8.3 Remove Navy & Slate as Binding Design Direction

Do not keep Navy & Slate as an architecture requirement.

It can be a temporary design idea only.

## 8.4 Remove Undefined Admin Role

Do not use “Admin” unless officially defined.

For MVP:

```text
Owner = highest authority
Accountant = financial/admin operational authority
```

If a System Admin role is needed later, define it explicitly.

## 8.5 Clean Import Workbook Sheets Are Future Templates

The clean import sheet list should be labeled as:

```text
future normalized import template
```

not as the structure of the current workbook.

The current migration must be workbook-specific.

# 11. Delivery Risk Control

Do not hand this ERP directly to the client as a full Excel replacement on day one.

Recommended rollout:

1. Demo with fake or copied data.
2. Pilot with limited real data.
3. Parallel run with Excel.
4. Reconciliation between ERP and Excel.
5. User training.
6. Go-live only after matching critical balances.
7. Production hosting upgrade before serious usage.

```text
simple for the current client

future-ready where productization matters
not over-configurable in MVP
not financially dangerous
not confusing for workers
not dependent on AI assumptions during coding
```
